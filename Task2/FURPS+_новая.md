# FURPS+ требования. MVP открытия депозитов. Банк «Стандарт»

| Код | Требования | Комментарий |
|-----|------------|-------------|
| F   | Функциональные (Functionality) | |
| F1  | На сайте новый клиент видит список доступных депозитов с актуальными ставками | |
| F2  | Клиент оставляет на сайте номер телефона и ФИО и подаёт заявку на депозит, после чего ему звонит менеджер кол-центра | |
| F3  | Менеджер кол-центра изучает заявку в системе кол-центра и может предложить клиенту особые условия | |
| F4  | В интернет-банке клиент видит актуальные ставки и персонализированные ставки лично для него | |
| F5  | В интернет-банке клиент указывает счёт и сумму, подаёт заявку на открытие депозита и подтверждает операцию СМС-кодом | |
| F6  | Ставки по депозитам ведутся в едином хранилище вместо XLS-файлов, с ними работают сотрудники бэк-офиса депозитов и бэк-офиса кредитов | |
| F7  | В АБС есть процесс согласования и подтверждения ставки и условий по заявке, в MVP заявку обрабатывает менеджер бэк-офиса | |
| F8  | Клиент получает СМС-уведомления после подтверждения ставки и после открытия депозита | |
| F9  | Все клиентские каналы (сайт, интернет-банк, кол-центр) получают актуальные ставки из единого источника и показывают одинаковые значения | Доп требование. Ставки обновляются каждый день и сейчас лежат в XLS. Если каждый канал возьмёт их по-своему, на сайте и в интернет-банке клиент увидит разные ставки. Поэтому все каналы должны читать актуальную ставку из одного источника |
| U   | Удобство использования (Usability) | |
| U1  | Интерфейс подачи заявки и открытия депозита должен быть максимально удобным для клиента | |
| U2  | Приложения следуют принятой в компании системе дизайна, клиент видит привычные цвета и брендированные элементы | |
| R   | Надёжность (Reliability) | |
| R1  | Сервисы депозитного процесса работают круглосуточно с доступностью не ниже 99,9% | |
| R2  | Интернет-банк переживает сбой ЦОД, при отказе основной площадки сервисы продолжают работать на резервном ЦОД и выдерживают нагрузку | |
| P   | Производительность (Performance) | |
| P1  | Отклик по операциям измеряется миллисекундами | |
| P2  | Справочные данные загружаются быстрее одной секунды | |
| P3  | Система масштабируется горизонтально | |
| S   | Поддерживаемость (Supportability) | |
| S1  | Для дальнейшего расширения системы разрабатывается документация | |
| S2  | Архитектура готова к расширению, интернет-банк в части депозитов переводится на микросервисы | |
| S3  | Доработки делаются на технологиях, по которым в банке уже есть экспертиза | |
| +R  | + Ограничения (Restrictions) | |
| +R1 | Чувствительные данные с сайта и в интернет-банке передаются по защищённому каналу с шифрованием трафика (HTTPS/TLS) | |
| +R2 | При доработках максимально используются существующие технологии банка, прежде всего MS SQL и Oracle, новые технологии допустимы только при совместимости с текущими платформами и наличии экспертизы внутри банка | |
| +R3 | Для очередей сообщений используется Kafka на перспективу, но текущая платформа интернет-банка с Kafka несовместима, поэтому часть интернет-банка под задачу депозитов выносится на микросервисную архитектуру | |
| +R4 | Функционал работы с СМС реализуется силами команды разработки банка без доработки ядра подрядчиком | |
| +R5 | Интернет-банк в новом процессе не работает напрямую с API и базой данных АБС | |
| +R6 | АБС масштабируется только вертикально | |
| +R7 | Новый клиент проходит идентификацию офлайн в отделении | |
| +R8 | Сотрудники бэк-офиса депозитов и бэк-офиса кредитов не имеют доступа к данным друг друга | Доп требование. Из процесса создания депозита. Процесс выглядит так, потому что сотрудники депозитов и сотрудники кредитов не должны иметь доступа к данным друг друга по требованиям безопасности. именно поэтому сейчас ставки согласуют письмами. Это определяет права доступа к будущему сервису ставок |
